# 09-系统设计题案例库

> 系统设计题是 AI 面试中最能拉开差距的环节。它不考你背了多少概念，而考你能不能把零散知识串成方案、能不能权衡不同选择、能不能考虑边界情况。

这一章提供 5 个完整的系统设计题案例，每个案例都包含：
- 需求澄清
- 核心挑战
- 架构设计
- 关键决策
- 扩展与权衡

建议用法：先自己尝试回答，再看参考答案，最后对比差距在哪里。

---

## 怎么准备系统设计题

### 1. 不要背答案，要学框架

系统设计题变化很多，但核心框架是稳定的：

```
1. 需求澄清（确认范围，不要一上来就画架构）
2. 核心挑战（点出这道题的难点在哪里）
3. 架构设计（分层讲，不要一锅端）
4. 关键决策（为什么这样选，有没有考虑过其他方案）
5. 扩展与权衡（如果 XX 变了，架构要怎么调整）
```

### 2. 练习时强制自己画草图

哪怕是在纸上画，也要有：
- 数据流向
- 模块划分
- 关键组件

因为面试官想看的是你的**系统思维**，不是你的记忆力。

### 3. 每道题准备 3 个关键决策

系统设计题的核心不是"标准答案"，而是你的**决策理由**。

比如：
- 为什么用混合检索而不是纯向量检索
- 为什么分块要按文档类型区分
- 为什么在检索后做权限过滤而不是检索前

## 案例 1：设计一个支持 10 万文档的企业知识库系统

### 题目

> 公司想建立一个内部知识库系统，支持 10 万 + 技术文档的智能问答。文档类型包括 PDF、Word、Markdown 和代码文件。请设计系统架构。

---

### 1. 需求澄清

> 我先确认几个问题：
> - 主要使用场景是？（内部检索、客服问答、研发支持？）
> - 有没有权限控制需求？（不同部门看不同文档？）
> - 响应时间要求？（实时查询还是离线分析？）
> - 需不需要支持多轮对话？

**假设**：这是一个内部研发支持系统，需要权限控制，响应时间要求秒级，单轮问答为主。

---

### 2. 核心挑战

> 基于常见场景，我认为主要挑战是：
> - 文档类型多样，解析和分块策略要灵活
> - 检索质量要求高，不能总返回不相关内容
> - 权限控制要细粒度，不同人看不同内容
> - 索引更新要高效，新文档能快速可查

---

### 3. 架构设计

```

│                     应用层                               │
│  ┌───────────┐  ┌───────────┐  ┌───────────────────┐   │

                          ↓

│  │ (向量+BM25)│  │ (Rerank)  │  │ (基于用户角色)    │   │
│  └───────────┘  └───────────┘  └───────────────────┘   │
└─────────────────────────────────────────────────────────┘

│  └───────────┘  └───────────┘  └───────────────────┘   │
└─────────────────────────────────────────────────────────┘

│  │ (按类型)  │  │ (按类型)  │  │                   │   │

└─────────────────────────────────────────────────────────┘

**各层职责**：

| 层级 | 职责 | 关键组件 |
|------|------|----------|
| 文档处理层 | 解析、清洗、分块、向量化 | PyPDF2、python-docx、自定义分块器、Embedding 模型 |
| 索引层 | 存储向量、关键词、元数据 | FAISS、Elasticsearch、PostgreSQL |
| 检索层 | 检索、重排序、权限过滤 | 混合检索器、Cross-Encoder Rerank、权限中间件 |
| 应用层 | 问答接口、引用展示、反馈 | FastAPI、前端组件、评估日志 |

---

### 4. 关键决策

#### 决策 1：为什么用混合检索？

> 纯向量检索对语义相似的问题效果好，但对专业术语、配置项、API 名称这类精确匹配效果差。
> 
> 比如用户问"如何配置 max_connections 参数"，向量检索可能返回一堆"连接池"相关内容，但 BM25 能精准命中包含"max_connections"的文档。
> 
> 所以采用**向量检索 (召回) + BM25(召回) → 重排序**的混合方案，两者召回结果合并后用 Cross-Encoder 重排序。

#### 决策 2：为什么分块要按文档类型区分？

> API 文档适合按函数/类分块（每个函数一个 chunk），操作手册适合按章节分块，代码文件适合按函数 + 注释分块。
> 
> 统一分块会割裂上下文——比如把一个函数的签名和实现分到两个 chunk，检索时可能只命中其中一个，导致信息不完整。
> 
> 所以设计了 3 套分块规则：
> - API 文档：按函数/类边界分块，保留完整签名
> - 操作手册：按章节分块，每块 500-800 字
> - 代码文件：按函数分块，保留函数名和关键注释

#### 决策 3：权限怎么控制？

> 在检索后做过滤，而不是检索前。
> 
> 原因是：向量检索需要完整的召回空间，如果在检索前就过滤，可能漏掉相关内容。
> 
> 做法是：
> - 文档入库时打上权限标签（部门、职级、项目）
> - 检索时先召回 Top 50
> - 用用户权限标签过滤，保留 Top 20
> - 再送 Rerank 重排序

---

### 5. 扩展与权衡

| 变化 | 架构调整 |
|------|----------|
| 文档量从 10 万→1000 万 | 分片索引、分布式 FAISS、加缓存层 |
| 响应时间从秒级→毫秒级 | 语义缓存、预计算热门查询、CDN 静态资源 |
| 支持多语言 | 换多语言 Embedding 模型、分块考虑语言边界 |
| 需要多轮对话 | 加对话历史管理、上下文窗口控制、指代消解 |

---

### 面试回答示例（3 分钟版本）

> "我会把系统分成 4 层：文档处理、索引、检索、应用。
> 
> **文档处理层**按文档类型设计不同分块策略——API 文档按函数分块，操作手册按章节分块，因为统一分块会割裂上下文。
> 
> **索引层**用向量索引 + 关键词索引的混合方案，因为纯向量检索对专业术语效果差，加 BM25 可以互补。
> 
> **检索层**做三件事：混合检索召回、权限过滤、重排序。权限在检索后过滤，避免漏掉相关内容。
> 
> **应用层**提供问答接口、引用展示和反馈收集，用于持续优化。
> 
> 关键挑战是检索质量和权限控制的平衡，我的方案是先召回再过滤再重排序，保证既安全又准确。"

## 案例 2：设计一个 AI 代码审查助手

### 题目

> 公司想建立一个 AI 代码审查系统，能自动审查 Pull Request，给出改进建议。请设计系统架构。

---

### 1. 需求澄清

> 我先确认几个问题：
> - 支持哪些编程语言？
> - 审查重点是？（代码规范、性能问题、安全漏洞、业务逻辑？）
> - 集成到哪里？（GitHub、GitLab、内部系统？）
> - 需要人工确认吗？还是直接提交评论？

**假设**：主要支持 Python/JavaScript，审查重点是代码规范 + 潜在 Bug，集成到 GitHub，审查结果先给人看再提交评论。

---

### 2. 核心挑战

> 主要挑战是：
> - 代码审查需要理解上下文，不是单文件分析
> - 误报率要控制，不然开发者会忽略所有建议
> - 需要区分"规范问题"和"逻辑问题"，前者可以自动提，后者需要人工确认
> - 响应时间要快，不能阻塞 PR 流程

---

### 3. 架构设计

```
┌─────────────────────────────────────────────────────────┐
│                    GitHub 集成层                          │
│  ┌───────────┐  ┌───────────┐  ┌───────────────────┐   │
│  │ Webhook   │  │ PR  diff   │  │ 评论提交          │   │
│  │ 监听      │  │ 提取      │  │ (需人工确认)      │   │
│  └───────────┘  └───────────┘  └───────────────────┘   │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│                    代码分析层                            │
│  ┌───────────┐  ┌───────────┐  ┌───────────────────┐   │
│  │ AST 解析  │  │ 依赖图    │  │ 变更影响分析      │   │
│  │           │  │           │  │                   │   │
│  └───────────┘  └───────────┘  └───────────────────┘   │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│                    规则引擎层                            │
│  ┌───────────┐  ┌───────────┐  ┌───────────────────┐   │
│  │ 静态规则  │  │ AI 模型   │  │ 安全扫描          │   │
│  │ (lint)    │  │ (LLM)     │  │ (SAST)            │   │
│  └───────────┘  └───────────┘  └───────────────────┘   │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│                    结果聚合层                            │
│  ┌───────────┐  ┌───────────┐  ┌───────────────────┐   │
│  │ 去重合并  │  │ 优先级排序│  │ 人工审核界面      │   │
│  └───────────┘  └───────────┘  └───────────────────┘   │
└─────────────────────────────────────────────────────────┘
```

---

### 4. 关键决策

#### 决策 1：为什么用"规则引擎 + AI 模型"混合方案？

> 纯规则引擎（如 linter）准确率高但只能抓固定模式，纯 AI 模型灵活但误报率高。
> 
> 混合方案：
> - 静态规则抓规范问题（命名、格式、imports）——准确率高，直接提
> - AI 模型抓逻辑问题（潜在 Bug、优化建议）——灵活，但需要人工确认
> - 安全扫描用专业 SAST 工具——更可靠

#### 决策 2：如何控制误报率？

> - 设置置信度阈值，低于阈值的建议不提交
> - 对同一问题的多条建议去重合并
> - 允许开发者标记"误报"，系统学习后不再提类似问题
> - 按文件类型调整策略——测试文件放宽，核心业务代码从严

#### 决策 3：如何理解代码上下文？

> 不是单文件分析，而是：
> - 用 AST 解析代码结构
> - 构建函数调用图
> - 分析 PR diff 的影响范围（哪些函数被调用）
> - 把相关代码一起送给 LLM，而不是只送变更行

---

### 5. 扩展与权衡

| 变化 | 架构调整 |
|------|----------|
| 支持更多语言 | 加对应语言的 AST 解析器、规则库 |
| 需要自动提交评论 | 加白名单机制（可信开发者直接提，新人需审核） |
| 集成到 GitLab | 适配 GitLab API，逻辑不变 |
| 需要学习团队规范 | 加反馈学习模块，记录团队接受/拒绝的建议 |

## 案例 3：设计一个多 Agent 协作平台

### 题目

> 公司想建立一个多 Agent 协作平台，支持多个 AI Agent 分工完成复杂任务。请设计系统架构。

---

### 1. 需求澄清

> 我先确认几个问题：
> - Agent 是预定义的还是用户可以自定义？
> - 协作流程是固定的还是动态编排？
> - 需要持久化状态吗？（任务中断后能恢复）
> - 需要人工介入吗？（某些步骤需要人确认）

**假设**：支持预定义 + 自定义 Agent，流程可动态编排，需要持久化状态，支持人工介入。

---

### 2. 核心挑战

> 主要挑战是：
> - Agent 之间的通信和状态同步
> - 任务拆解和分配策略
> - 错误处理和恢复机制
> - 如何避免 Agent 无限循环或死锁

---

### 3. 架构设计

```
┌─────────────────────────────────────────────────────────┐
│                    编排层                                │
│  ┌───────────┐  ┌───────────┐  ┌───────────────────┐   │
│  │ 流程定义  │  │ 任务拆解  │  │ 状态机管理        │   │
│  │ (YAML)    │  │ (Planner) │  │ (持久化)          │   │
│  └───────────┘  └───────────┘  └───────────────────┘   │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│                    Agent 管理层                          │
│  ┌───────────┐  ┌───────────┐  ┌───────────────────┐   │
│  │ Agent 注册│  │ 能力描述  │  │ 负载均衡          │   │
│  │           │  │           │  │                   │   │
│  └───────────┘  └───────────┘  └───────────────────┘   │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│                    执行层                                │
│  ┌───────────┐  ┌───────────┐  ┌───────────────────┐   │
│  │ 工具调用  │  │ 消息总线  │  │ 人工介入点        │   │
│  │           │  │           │  │                   │   │
│  └───────────┘  └───────────┘  └───────────────────┘   │
└─────────────────────────────────────────────────────────┘
```

---

### 4. 关键决策

#### 决策 1：流程是固定的还是动态的？

> 采用**混合模式**：
> - 预定义流程：用 YAML 定义常见工作流（如文档处理、数据分析）
> - 动态编排：Planner Agent 根据任务动态拆解和分配
> 
> 原因是：固定流程稳定可靠，动态编排灵活但不可控。混合模式兼顾两者。

#### 决策 2：如何持久化状态？

> 每个任务有状态机：
> ```
> Pending → Running → (WaitingHuman | Failed | Completed)
> ```
> 
> 状态持久化到数据库，包括：
> - 当前步骤
> - 已执行动作
> - Agent 之间的消息历史
> - 等待人工确认的数据
> 
> 这样任务中断后可以从断点恢复。

#### 决策 3：如何避免无限循环？

> - 设置最大步数限制（如 50 步）
> - 检测重复状态（同样的输入→同样的输出→终止）
> - Planner 做循环检测，发现循环时切换策略
> - 人工介入点：复杂任务设置必须人工确认的节点

## 案例 4：设计一个 AI 应用成本监控系统

### 题目

> 公司 AI 应用的 Token 消耗快速增长，需要建立一个成本监控系统。请设计系统架构。

---

### 1. 需求澄清

> 我先确认几个问题：
> - 监控范围？（所有 AI 调用还是特定服务）
> - 需要实时告警吗？
> - 需要按部门/项目分摊成本吗？
> - 需要优化建议吗？

**假设**：监控所有 AI 调用，需要实时告警，需要按项目分摊，需要提供优化建议。

---

### 2. 核心挑战

> 主要挑战是：
> - Token 计数要准确（不同模型计价不同）
> - 告警要及时，但不能太敏感（避免告警疲劳）
> - 成本分摊需要合理的 attribution 策略
> - 优化建议要具体，不能只说"少用点"

### 4. 关键决策

#### 决策 1：Token 计数怎么做到准确？

> - 在 SDK 层埋点，记录每次调用的 input_tokens 和 output_tokens
> - 不同模型用不同计价表（如 GPT-4 和 GPT-3.5 价格不同）
> - 缓存命中也要记录（虽然不产生 Token，但影响成本分析）

#### 决策 2：告警策略怎么设计？

> 三层告警：
> - **预警**：日消耗达到预算的 80% —— 通知项目负责人
> - **告警**：日消耗达到预算的 100% —— 通知 + 限流建议
> - **紧急**：小时消耗异常（如 10 倍于平均值）—— 立即通知 + 自动降级
> 
> 避免告警疲劳：同一问题 24 小时内不重复告警。

#### 决策 3：优化建议怎么生成？

> 基于数据分析：
> - 发现某项目重复查询多 → 建议加语义缓存
> - 发现某服务大量调用高价模型 → 建议评估是否可用低价模型替代
> - 发现某 Prompt 输出过长 → 建议精简 Prompt 或限制 max_tokens
> - 发现某时段消耗峰值 → 建议错峰调度

## 案例 5：设计一个 RAG 系统评估平台

### 题目

> 公司 RAG 系统上线后效果不稳定，需要建立一个评估平台来持续监控和优化。请设计系统架构。

---

### 1. 需求澄清

> 我先确认几个问题：
> - 评估指标有哪些？（准确率、召回率、延迟、用户满意度？）
> - 评估数据从哪来？（人工标注、用户反馈、自动评估？）
> - 需要 A/B 测试吗？
> - 评估频率？（实时、每天、每周？）

**假设**：评估指标包括检索准确率、答案质量、延迟；数据来源包括人工标注集 + 用户反馈；需要 A/B 测试；每天自动评估 + 实时用户反馈。

---

### 2. 核心挑战

> 主要挑战是：
> - 答案质量很难自动评估（需要人工或 LLM 判断）
> - 评估集需要持续更新（不然会过拟合）
> - 用户反馈噪声大（需要清洗和加权）
> - A/B 测试需要流量分割和统计显著性检验

---

### 3. 架构设计

```
┌─────────────────────────────────────────────────────────┐
│                    数据层                                │
│  ┌───────────┐  ┌───────────┐  ┌───────────────────┐   │
│  │ 评估集管理│  │ 用户反馈  │  │ 线上日志          │   │
│  │ (人工标注)│  │ (清洗加权)│  │ (请求 - 响应对)   │   │
│  └───────────┘  └───────────┘  └───────────────────┘   │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│                    评估层                                │
│  ┌───────────┐  ┌───────────┐  ┌───────────────────┐   │
│  │ 检索评估  │  │ 答案评估  │  │ 端到端评估        │   │
│  │ (Recall@K)│  │ (LLM 评判)│  │ (用户满意度)      │   │
│  └───────────┘  └───────────┘  └───────────────────┘   │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│                    实验层                                │
│  ┌───────────┐  ┌───────────┐  ┌───────────────────┐   │
│  │ A/B 测试  │  │ 版本管理  │  │ 统计显著性检验    │   │
│  │           │  │ (Prompt/  │  │                   │   │
│  │           │  │  模型/检索)│  │                   │   │
│  └───────────┘  └───────────┘  └───────────────────┘   │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│                    可视化层                              │
│  ┌───────────┐  ┌───────────┐  ┌───────────────────┐   │
│  │ 指标大盘  │  │ 问题诊断  │  │ 优化建议          │   │
│  │           │  │           │  │                   │   │
│  └───────────┘  └───────────┘  └───────────────────┘   │
└─────────────────────────────────────────────────────────┘
```

---

### 4. 关键决策

#### 决策 1：答案质量怎么评估？

> 三层评估：
> - **自动评估**：用 LLM 评判答案质量（一致性、相关性、完整性）
> - **人工抽检**：每天随机抽 50 条人工标注
> - **用户反馈**：点赞/点踩 + 可选评论，加权计入评估
> 
> LLM 评判 prompt 示例：
> ```
> 请评估以下 RAG 回答的质量：
> - 问题：{question}
> - 检索到的文档：{context}
> - 模型回答：{answer}
> 
> 评分维度（1-5 分）：
> 1. 相关性：回答是否针对问题
> 2. 准确性：回答是否与文档一致
> 3. 完整性：是否覆盖了关键信息
> 4. 可理解性：表达是否清晰
> ```

#### 决策 2：评估集怎么管理？

> - 初始评估集：人工标注 200-500 条代表性问题
> - 每周更新：从线上日志中挑选新的典型问题加入
> - 版本管理：评估集版本与系统版本对应，方便回溯
> - 分层抽样：按问题类型、难度、文档类型分层，保证覆盖

#### 决策 3：A/B 测试怎么做？

> - 流量分割：按用户 ID 哈希，50% A 组 50% B 组
> - 测试周期：至少 7 天，覆盖工作日和周末
> - 显著性检验：用 t 检验判断差异是否显著（p<0.05）
> - 多指标综合：不只看准确率，也看延迟、用户满意度

## 小结：系统设计题的通用框架

5 个案例虽然场景不同，但都遵循同一个框架：

```
1. 需求澄清 —— 确认范围，不要一上来就画架构
2. 核心挑战 —— 点出这道题的难点在哪里
3. 架构设计 —— 分层讲，不要一锅端
4. 关键决策 —— 为什么这样选，有没有考虑过其他方案
5. 扩展与权衡 —— 如果 XX 变了，架构要怎么调整
```

练习建议：
- 每道题先自己尝试回答，再看参考答案
- 强制自己画草图，培养系统思维
- 每道题准备 3 个关键决策理由
- 找人对练，让对方追问"为什么"

系统设计题没有标准答案，但有**好的思考框架**。把框架练熟了，遇到新题也能应对。
