# 05-项目建议

> 这一章的重点，不只是“给你几个项目题目”，而是帮你回答一个更关键的问题：**什么样的 AI 项目，才真的值得写进简历、拿去面试讲、变成你的能力证明。**

很多人做了项目，却在面试里讲不出来；也有人项目看起来很多，但本质上只是把教程重新做了一遍。真正有价值的，不是项目数量，而是：

- 你为什么选这个项目
- 你解决了什么问题
- 你做了哪些关键设计
- 你踩过哪些坑
- 你如何证明这个项目不是 demo 拼装

这章会从“项目选择”走到“项目表达”，把项目当作能力载体，而不是完成任务清单。

---

## 先明确一个判断：什么项目值得做

### 好项目的 5 个标准

#### 1. 能说明真实问题
一个好项目，最好不是“为了做而做”，而是能回答：
- 它解决了什么问题？
- 为什么值得做？
- 谁会真正使用它？

哪怕只是一个个人项目，也最好有明确场景，比如：
- 个人知识库问答
- 团队文档检索
- 代码审查辅助
- 数据分析助手
- 面试准备与知识整理

#### 2. 能体现你的关键能力
项目不一定要很大，但一定要能映射能力。

比如：
- 做 RAG 项目，可以体现检索、分块、召回、答案引用
- 做 Agent 项目，可以体现工具调用、流程设计、状态管理
- 做工程化项目，可以体现部署、评估、监控、权限设计

#### 3. 能被讲清楚
如果一个项目你自己都说不明白，大概率就不适合写进简历。

面试里最常见的问题不是“你做过吗”，而是：
- 为什么这样设计？
- 为什么不用别的方案？
- 遇到什么问题？
- 你怎么验证效果？

所以一个能讲清楚的项目，通常比一个堆了很多技术词的项目更值钱。

#### 4. 有取舍，不是功能乱堆
AI 项目很容易变成“什么都想加一点”，最后像一个功能清单。

真正好的项目往往有清晰边界：
- 核心用户是谁
- 核心问题是什么
- 先解决哪一层问题
- 哪些功能是暂时不做的

这种“有取舍”的项目，面试时反而更有说服力。

#### 5. 能留下证据
项目最好能留下可验证的东西，比如：
- GitHub 仓库
- README
- 架构图
- 在线 demo
- 截图 / 录屏
- 指标对比
- 问题复盘

因为最终面试官看到的，不是你脑海中的项目，而是你呈现出来的项目。

---

## 哪些项目不太值得写进简历

下面这些项目，不是完全不能做，而是通常不够构成核心亮点：

### 1. 纯 API 套壳项目
例如：
- 调一个模型 API 做聊天框
- 接一个现成模板生成页面
- 没有检索、没有流程、没有评估、没有设计思考

这类项目可以作为练手，但通常不适合作为核心项目写进简历。

### 2. 完全照教程复刻的项目
如果你的项目和公开视频 / 教程一模一样，而且你讲不出自己做了什么改动，那么面试价值会很弱。

### 3. 只能演示“能跑”，不能说明“为什么这样做”的项目
很多项目能跑，但没有设计理由：
- 为什么用这个向量库
- 为什么这样切 chunk
- 为什么要加 rerank
- 为什么用单 Agent 而不是工作流

这种项目很难撑住深入追问。

### 4. 功能太多但没有主线的项目
AI 项目最怕“看起来什么都有，实际上什么都不深”。

如果一个项目同时写了：
- RAG
- Agent
- 多模态
- 语音
- 多角色协作
- 自动部署

但每块都只点到为止，面试里往往会被一问就散。

---

## 做项目时，应该优先展示什么能力

对于 AI 岗位相关项目，通常优先展示这 4 层能力：

### 1. 问题抽象能力
你能不能把真实需求抽象成一个可落地的问题。

例如：
- 不是“做一个 RAG 项目”
- 而是“让团队内部文档能被稳定检索与引用”

### 2. 系统设计能力
你能不能解释系统由哪些部分组成，它们为什么这样组合。

例如：
- 文档解析
- 分块策略
- 检索与重排
- 模型回答
- 引用溯源
- 评估与反馈

### 3. 工程实现能力
你能不能真的把它做出来，并处理工程细节。

例如：
- 数据脏怎么办
- 接口超时怎么办
- token 成本怎么控
- 召回不准怎么调
- 响应速度慢怎么办

### 4. 复盘与表达能力
你能不能总结：
- 做对了什么
- 做错了什么
- 下次会怎么改

这类表达，往往最能体现“成熟度”。

## 项目选择建议：按阶段来做

## 5.1 入门级项目：先建立完整闭环

适合：
- 刚开始接触 AI 应用开发
- 还没有拿得出手的项目
- 需要快速做出第一个可讲项目的人

目标不是做复杂，而是做完整。

### 推荐方向 1：个人知识库问答助手

**适合展示的能力**：
- RAG 基本流程
- 文档解析与分块
- 向量检索
- 引用与答案展示

**为什么值得做**：
- 有明确使用场景
- 技术栈不算太重
- 容易做出演示效果
- 很适合作为第一个 AI 应用项目

**建议重点讲什么**：
- 文档如何切分
- 检索效果如何优化
- 为什么要展示引用来源
- 如何避免模型胡说

### 推荐方向 2：AI 代码审查助手

**适合展示的能力**：
- 代码理解
- Prompt 设计
- GitHub / PR 流程接入
- 规则化审查与结果输出

**为什么值得做**：
- 更贴近工程场景
- 对后端 / 工程方向很友好
- 能讲代码质量、安全、可维护性

**建议重点讲什么**：
- 怎么定义“审查维度”
- 如何避免泛泛而谈
- 如何提高意见可执行性
- 如何处理误报

### 推荐方向 3：智能待办 / 工作助理

**适合展示的能力**：
- 工具调用
- 任务结构化
- 状态管理
- 用户交互设计

**为什么值得做**：
- Agent 感比较强
- 功能闭环清晰
- 非常适合展示“自然语言 → 系统动作”的转化

**建议重点讲什么**：
- 如何把自然语言转成结构化任务
- 如何管理时间、提醒和优先级
- 如何保证多轮交互中的状态一致性

---

## 5.2 进阶级项目：开始体现系统能力

适合：
- 已经做过 1-2 个基础项目
- 想让项目更有技术深度
- 想从“能做 demo”走向“能做系统”的人

### 推荐方向 4：多文档智能分析系统

**适合展示的能力**：
- 多源文档处理
- 信息抽取
- 跨文档对比
- 自动摘要与报告生成

**为什么值得做**：
- 很适合金融、研究、企业分析等场景
- 能体现复杂输入处理能力
- 可以讲信息提炼与结果结构化

**建议重点讲什么**：
- 多文档场景为什么比单文档难
- 如何做结构化抽取
- 如何降低摘要失真
- 报告生成怎么兼顾准确性与可读性

### 推荐方向 5：AI 研究助手

**适合展示的能力**：
- 多步任务流程
- 搜索、筛选、摘要、归纳
- Agent 工具链设计
- 长流程任务拆解

**为什么值得做**：
- 非常适合展示 Agent 设计能力
- 可以讲任务规划、工具协同和结果整合
- 能体现“从资料到知识”的能力

**建议重点讲什么**：
- 工具链是怎么设计的
- 如何做论文筛选
- 如何控制摘要质量
- 如何把结果沉淀成结构化综述

### 推荐方向 6：智能数据分析助手

**适合展示的能力**：
- 代码生成与执行
- 数据分析流程设计
- 图表生成
- 用户查询理解

**为什么值得做**：
- 商业价值明确
- 展示“模型 + 执行器”的组合能力
- 很容易讲出实际应用场景

**建议重点讲什么**：
- 如何把自然语言转成可执行分析
- 怎么约束生成代码的安全性
- 如何处理错误结果与异常数据

---

## 5.3 高级项目：开始体现工程化与产品感

适合：
- 希望冲更强的工程岗 / 平台岗 / AI 应用架构岗
- 想做能拉开差距的作品集项目

### 推荐方向 7：企业级知识库系统

**适合展示的能力**：
- 企业 RAG 架构
- 权限与审计
- 索引更新
- 检索质量与监控
- 工程化部署

**为什么值得做**：
- 很接近真实业务系统
- 能体现完整工程能力
- 很适合讲“从 demo 到生产”的差异

**建议重点讲什么**：
- 为什么企业知识库不是“上传文档 + 检索”这么简单
- 权限、索引更新、审计日志为什么重要
- 如何评估问答质量与系统稳定性

### 推荐方向 8：多 Agent 协作平台

**适合展示的能力**：
- 角色拆分
- 工作流设计
- 并行 / 串行任务编排
- 结果汇总与可视化

**为什么值得做**：
- 很适合展示复杂系统抽象能力
- 可以讲“为什么需要多 Agent”而不是盲目追热点
- 对架构表达特别加分

**建议重点讲什么**：
- 多 Agent 到底解决了什么问题
- 角色边界怎么划分
- 如何避免协作成本大于收益
- 什么时候单 Agent 更合适

### 推荐方向 9：面向真实业务的 AI 工作台

例如：
- 销售助手
- 客服助手
- 内部知识运营台
- 内容生成与审核工作台

**适合展示的能力**：
- 业务理解
- 产品设计
- 多模块协同
- 结果可控性与人工介入设计

**为什么值得做**：
- 很能体现“懂业务 + 懂技术”
- 比单点 demo 更接近真实团队需要

---

## 不同方向的人，项目应该怎么选

### 如果你偏后端 / 工程
优先做：
- 企业级知识库系统
- AI 代码审查助手
- 智能数据分析助手

因为这些项目更容易体现：
- 系统设计
- 工程稳定性
- 接口与服务组织能力

### 如果你偏应用 / 产品
优先做：
- 智能待办 / 工作助理
- AI 工作台
- AI 研究助手

因为这些项目更容易体现：
- 场景理解
- 交互设计
- 功能取舍
- 产品感

### 如果你偏算法 / 研究
优先做：
- 多文档分析系统
- RAG 评估与优化项目
- 检索 / 重排 / 生成质量对比实验

因为这些项目更容易体现：
- 方法选择
- 指标意识
- 实验设计
- 结果分析

## 项目写进简历时，最容易犯的错

### 错误 1：只写技术栈，不写问题
例如：
- 使用 LangChain、FAISS、OpenAI API、FastAPI 搭建系统

这句不算错，但它没有告诉面试官：
**你到底解决了什么问题。**

更好的写法应该是：
- 面向团队内部文档检索场景，设计并实现了一个支持引用溯源的 RAG 问答系统，完成文档解析、分块检索、答案生成与结果展示闭环。

### 错误 2：只写功能，不写设计判断
例如：
- 实现了文档上传、问答、搜索、总结、导出等功能

这种写法看起来很多，但没有重点。

更好的方式是写：
- 为提升检索相关性，设计了“分块 + 向量检索 + 引用展示”的问答流程，并针对召回不准问题做了分块策略调整与 Prompt 优化。

### 错误 3：只说做了，不说效果
即使没有真实用户量，也可以写：
- 响应时间优化到多少
- 检索命中率如何改善
- 支持了哪些文档类型
- 在什么测试集上做了什么比较

### 错误 4：把项目写成“流水账”
项目描述不是把你干过的每一步都写出来，而是要形成：
- 场景
- 方案
- 关键难点
- 结果

## 一个更实用的项目表达模板

你可以尝试用下面这个结构讲项目：

### 1. 背景
为什么做这个项目？场景是什么？

### 2. 目标
你想解决什么问题？核心目标是什么？

### 3. 方案
系统由哪些部分组成？为什么这么设计？

### 4. 难点
真正难的地方是什么？你怎么处理的？

### 5. 结果
项目达到了什么效果？哪怕是阶段性效果也要说。

### 6. 反思
如果再做一遍，你会怎么优化？

这个结构很适合写：
- README
- 简历项目描述
- 面试中的项目介绍
- 复盘文档

## 如果你现在只能做一个项目，建议怎么选

### 时间只有 1-2 周
优先做：
- 个人知识库问答助手
- 智能待办 / 工作助理

目标：
先做出完整闭环，确保自己能讲清楚。

### 时间有 3-4 周
优先做：
- 多文档分析系统
- AI 研究助手
- 智能数据分析助手

目标：
开始体现系统设计与多模块协同。

### 时间有 1-2 月
优先做：
- 企业级知识库系统
- 多 Agent 协作平台
- 面向真实业务的 AI 工作台

目标：
把项目做成真正能体现工程能力和产品思维的作品集核心项目。

## 这一章最后想强调的一件事

做项目当然重要，但对面试更关键的是：

**你能不能把项目讲成自己的能力证明。**

很多人输在不会做项目，
但更多人其实输在：
- 项目没有主线
- 讲不出关键判断
- 说不清难点
- 无法把项目和岗位能力连起来

所以这章真正想帮你的，不只是“选项目”，而是：

- 选对项目
- 做成完整闭环
- 留下可验证证据
- 最后讲成一个有说服力的故事

这才是项目在 AI 面试里真正的价值。
