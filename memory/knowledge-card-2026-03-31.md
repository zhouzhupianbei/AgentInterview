# 知识卡片 - 2026-03-31

## 主题：AI 工程化不是"写更好的代码"，而是建立可观测、可评估、可迭代的系统

### 核心观察

这轮维护重点补强了 AI 工程化相关内容，源于一个持续的观察：

**很多开发者的能力停留在"能跑通 demo"，但真正的 AI 工程岗位要求理解从实验到生产的完整链路。**

面试时被问到"你的系统上线后怎么保障质量"，只回答"我用了 LangChain + RAG"是不够的。真正有深度的回答应该覆盖：
- 可观测性：每一次请求的完整链路追踪
- 评估体系：如何衡量输出质量，不只是延迟和错误率
- 成本控制：Token 消耗、模型分级、缓存策略
- 安全防护：输入过滤、输出审查、权限控制
- 持续迭代：Prompt 版本管理、用户反馈闭环

### AI 工程化的五个关键维度

| 维度 | 核心问题 | 常见实践 |
|------|----------|----------|
| 可观测性 | 出了问题知道哪里错了 | 链路追踪、P95 延迟监控、输出质量指标 |
| 评估体系 | 怎么衡量"效果好坏" | 离线评估集、在线用户反馈、人工抽检 |
| 成本控制 | Token 消耗失控怎么办 | 缓存、模型分级、Token 预算、Prompt 精简 |
| 安全防护 | 如何防止滥用和泄露 | 输入过滤、输出审查、权限控制、降级方案 |
| 持续迭代 | 如何持续优化效果 | Prompt 版本管理、评估指标趋势回顾、反馈闭环 |

### 一个实用的排查框架

RAG 系统上线后效果不如预期，按这个优先级排查：

```
1. 检索层问题（约 50%）
   → 检查 embedding 模型、chunk 策略、query 改写

2. Prompt 层问题（约 25%）
   → 优化 system prompt、增加约束、精简上下文

3. 模型层问题（约 15%）
   → 升级模型、领域微调、调整温度参数

4. 数据层问题（约 10%）
   → 清洗数据、补充文档、建立增量更新
```

### 面试中怎么讲 AI 工程化

建议按这个框架组织：

1. **先说核心挑战**：AI 系统输出不确定性 → 需要不同于传统软件的质量保障体系
2. **再讲 5 个维度**：挑 2-3 个展开（最好结合自己的经验）
3. **结合项目经验**：在项目里具体怎么做的（哪怕只做了其中一两个维度）
4. **最后讲思考**：你认为目前 AI 工程化最缺什么、最难的是什么

**示例回答**：
> "我做 RAG 系统时，最大的收获不是 LangChain 怎么用，而是意识到**demo 能跑和生产可用之间隔着整整一套工程体系**。
> 
> 比如我们上线第一周就发现，检索质量在实验环境测出来 85%，但线上用户反馈差很多。后来我们建了一个 50 题的评估集，每周回归测试，才发现是某些专业术语的召回率特别低。
> 
> 这件事让我理解到：AI 工程化不是'写更好的代码'，而是**建立一套可观测、可评估、可迭代的系统**。"
